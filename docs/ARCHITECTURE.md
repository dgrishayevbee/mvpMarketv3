# mvpMarket v2 — Архитектура прототипа

Вторая итерация прототипа. Первая версия — `dgrishayevbee/mvpMarket`,
её архитектурный документ остаётся там и описывает старую дизайн-систему.

## 1. Суть проекта

B2B маркетплейс-прототип. Единственный поставщик товаров в каталоге — сама
платформа. Роли покупатель/продавец переключаются как мок, без разграничения
прав на сервере. Без бэкенда, без БД, без реальной авторизации.

## 2. Отношение к первой версии

Переносится из v1 без изменений:

- слой состояния — все контексты в `src/context/`;
- `useLocalStorage`;
- контент главной — `src/data/siteContent.js`;
- карта роутов;
- конфигурация Vite и Vercel.

Пишется заново под новую дизайн-систему:

- `src/styles/tokens.css` — целиком из нового экспорта;
- UI-кит;
- вёрстка и разметка всех страниц;
- все CSS-файлы.

Из v1 не копируется CSS. Причина: перенесённая вёрстка тянет за собой
допущения старых токенов (размеры, ритм, радиусы) и новая ДС получается
натянутой на старый скелет.

## 3. Стек

React 19, Vite, React Router 7. Состояние — React Context поверх
localStorage, без Redux и без сервера. Стили — обычный CSS с переменными,
по файлу на компонент.

## 4. Роуты / страницы

| Роут | Страница | Эталон в ДС |
|---|---|---|
| `/` | Каталог сервисов + тарифные планы | «Экран · Каталог», «Тарифные планы» |
| `/product/:id` | Карточка решения | «Экран · Страница тарифа» |
| `/cart` | Корзина | строки списка |
| `/checkout` | Заявка на подключение | «Экран · Заявка на подключение» |
| `/login` | Вход | поля и формы |
| `/register` | Регистрация по ЭЦП | поля и формы |
| `/profile` | Личный кабинет | «Экран · Личный кабинет» |
| `/admin` | Редактор контента | поля и формы |
| `/seller`, `/seller/products`, `/seller/products/new`, `/seller/products/:id/edit`, `/seller/orders` | Кабинет поставщика | строки списка, метрики |

Сквозной поток прототипа: каталог → корзина → заявка → кабинет покупателя →
кабинет поставщика (там у заявки меняется статус).

## 5. Состояние приложения

Провайдеры вложены в `src/App.jsx` в порядке: Auth → Content → Products →
Cart → Favorites → Orders → UI.

- **AuthContext** — мок-авторизация, B2B-регистрация по ЭЦП (компания, БИН,
  подписант), режим продавца.
- **ContentContext** — контент главной поверх дефолтов из `siteContent.js`;
  сохранённая копия мержится с дефолтами, а не заменяет их.

  Важно про слияние: для массивов состав и порядок берутся из **сохранённой**
  копии — иначе удаление элемента в `/admin` не работало бы. Побочный
  эффект: правка состава массива в `siteContent.js` невидима всем, у кого
  уже есть копия в localStorage. Поэтому при изменении состава массивов
  обязательно поднимается `CONTENT_VERSION` — при несовпадении версии
  сохранённая копия отбрасывается до первого рендера. Новые ключи-объекты
  домешиваются сами и бампа не требуют.
- **ProductsContext** — товары, выведенные из контента.
- **CartContext** — единая корзина для всех точек добавления.
- **FavoritesContext**, **OrdersContext** — избранное и заказы.
- **UIContext** — состояние оверлеев. Пока не используется: в ДС оверлеев
  нет, корзина и заявка сделаны отдельными экранами. Провайдер оставлен,
  чтобы не переподключать его, когда оверлеи появятся.

Все ключи localStorage — с префиксом `mvpmarket:`.

## 6. Вёрстка / адаптив

Фокус — десктоп. Мобильные брейкпоинты добавляются позже, поэтому
layout- и контент-компоненты разделяются сразу.

### 6.1. Грабли вёрстки (проверять перед пушем)

Раздел перенесён из v1: ошибки в нём про CSS и flex, а не про дизайн-систему,
поэтому остаются актуальными. Пополняется каждый раз, когда правка ломает
страницу на живом сайте.

- **Центрирование блока внутри flex-колонки.** Если контейнер — это
  `display: flex; flex-direction: column`, то все его секции — flex-элементы.
  Связка `max-width: N` + `margin-inline: auto` на таком элементе отключает
  растягивание (`align-self: stretch`) и превращает его в shrink-to-fit блок:
  ширина схлопывается до контента, а grid-колонки `1fr` — до min-content.
  Так же ведут себя `align-self: center` и `width: fit-content`.
  Правильно — задавать **явную** ширину: `width: min(100%, N px)` плюс
  `margin-inline: auto`.
- **`height: 100%` на `#root` обрезает каркас.** Связка
  `html, body, #root { height: 100% }` фиксирует высоту корня по экрану:
  страница длиннее экрана переполняет его, и элементы каркаса, растянутые
  по высоте строки (сайдбар), обрываются на середине. Правильно —
  `height: 100%` только на `html, body`, а на `#root` — `min-height: 100%`.
  Поймано на каркасе v2: сайдбар заканчивался на 937px при странице 1798px.
- **Выравнивание строк между соседними карточками — это subgrid, а не
  одинаковая высота.** Пока каждая колонка была самостоятельным
  flex-столбцом, любая разница в содержимом (бейдж у одного пакета,
  сноска в две строки у другого) сдвигала вниз всё, что ниже. Помогает
  только общая сетка строк: родитель задаёт строки, колонка берёт
  `grid-row: span N` и `grid-template-rows: subgrid`, а части пакета лежат
  прямыми детьми колонки. Вложенные обёртки ломают это: выравниваются
  обёртки, а не строки внутри них.
- **Ширина колонки в `auto-fit` и точка перехода считаются вместе.** Если
  брейкпоинт поставить не там, где колонки перестают помещаться, на
  промежуточной ширине последняя колонка срывается в отдельный ряд и висит
  одна. Считать так: N × min-ширина + зазоры + сайдбар + поля = ширина окна,
  ниже которой нужен одноколоночный режим.
- **`width` не работает на flex-элементе с `flex-grow`.** Обратная сторона
  предыдущего пункта: если элемент растягивается (`flex: 1 1 0`), его
  собственная `width` игнорируется — размер по главной оси считает flex.
  Ограничивать ширину такого элемента надо через `max-width`, она клампит
  уже посчитанный размер. Поймано на `.content`: на 1920px рабочая область
  расползалась до 1714px вместо 1180px из Screen Template.
- **Прод-ветка = живой сайт.** Пуш в `main` сразу уходит в Vercel, поэтому
  layout-правку нельзя пушить «на глаз» — сначала проверка.

**Проверка layout-правки перед пушем** (обязательна, если менялись
`width`/`max-width`/`margin`/`display`/`grid-template`/`flex`):

1. `npm run dev`, открыть изменённую страницу.
2. Снять скриншоты на широком экране (~1920px) и на ~1280px — именно на
   широком вылезают ошибки центрирования и схлопывания.
3. Сверить: ширина карточек не изменилась (если задача была только про
   расположение), нет горизонтального скролла, поля слева/справа соразмерны.
4. Только после этого коммит и пуш.

В удалённой сессии Claude Code шаги 1-2 делаются без установки зависимостей:
Chromium и Playwright уже стоят в окружении
(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`), достаточно поднять dev-сервер
и снять скриншот скриптом во временной папке.

## 7. Дизайн-система

Beeline Business, экспорт Claude Design. Лежит в `docs/design-system/`:

- `Beeline Business DS.dc.html` — библиотека: токены, компоненты, эталонные
  экраны;
- `DS-BASE.md` — helmet-блок с токенами и сниппеты компонентов;
- `Screen Template.dc.html` — скелет экрана (топбар + сайдбар + рабочая
  область), по нему сделан `components/layout/Layout.jsx`;
- `DS-RULES.md` — правила стиля от автора системы.

Токены перенесены в `src/styles/tokens.css` один в один, включая имена
переменных. Компоненты читают переменные и не хардкодят значения, поэтому
следующая версия ДС меняет только этот файл.

Шрифты — Literata (serif, заголовки и метрики) и Golos Text (sans, весь
остальной текст), подключены в `index.html` с Google Fonts. В песочнице без
доступа в интернет они не грузятся и видно системный fallback — на Vercel
всё на месте.

Что осознанно не перенесено из библиотеки: карточка партнёра (у прототипа
единственный поставщик — сама платформа, независимых партнёров нет).

## 8. Запуск и деплой

```bash
npm install
npm run dev
```

Прод — Vercel, ветка `main`, автодеплой по пушу. `vercel.json` даёт SPA
fallback на `index.html`.
